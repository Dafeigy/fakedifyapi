# FakeDifyAPI 开发路线

## 1. 路线原则

- 第一阶段只实现已经确认的 Chatflow 串行聚合能力。
- 先稳定协议解析与事件状态机，再连接真实 Dify。
- 缺少真实 Chatflow 时使用模拟服务和协议夹具开发。
- 业务逻辑与 FastAPI/SSE 传输层分离，为未来并行化保留空间。
- 每个阶段必须有独立、可自动验证的验收条件。
- 开发规范确认前，不锁定代码目录、依赖管理、格式化和 CI 方案。

## 2. 阶段 0：开发规范确认

在正式编码前确定：

- Python 版本。
- 包和虚拟环境管理方式。
- 源码与测试目录结构。
- 命名、类型标注和异常处理约定。
- 格式化、lint、静态类型检查和测试工具。
- 配置及密钥加载方式。
- Git 分支、提交和评审规范。
- Docker 与部署目标。

交付物：

- 项目开发规范文档。
- 基础工具和目录约定。

验收条件：

- 后续阶段不会因基础规范缺失而产生互相冲突的实现方式。

## 3. 阶段 1：FastAPI 项目骨架

实现内容：

- FastAPI 应用入口。
- 健康检查端点。
- 配置模型和启动校验。
- 统一日志上下文。
- 网关 API Key 鉴权骨架。
- `/v1/chat-messages` 路由占位。
- `/v1/chat-messages/{task_id}/stop` 路由占位。

验收条件：

- 应用能够本地启动。
- 配置缺失时给出明确启动错误。
- 未授权调用被拒绝。
- 测试可以在不访问外部网络的情况下运行。

## 4. 阶段 2：Dify Chatflow 协议模型与 SSE 编解码

实现内容：

- Chatflow 请求模型。
- 公共 SSE 事件模型。
- Dify 子事件的宽松解析模型。
- SSE 增量解析器。
- SSE 序列化器。
- `event: ping` 支持。
- 跨 TCP chunk、跨行和大 `message_end` 的解析测试。
- 未知事件兼容策略。

验收条件：

- 任意网络分块方式下，同一组 SSE 输入都解析成相同事件序列。
- `message_end` 中的大型引用数组不会被截断。
- 未知字段不会导致整个流解析失败。
- 输出帧符合 `data: <json>\n\n` 或 `event: ping\n\n` 格式。

## 5. 阶段 3：模拟 Dify Chatflow

实现内容：

- 可配置的模拟 Chatflow 服务或测试应用。
- 正常流式响应场景。
- 多引用和无引用场景。
- 首字前失败、首字后失败和流中断场景。
- 延迟、ping 和大事件场景。
- 停止任务场景。
- 多轮 `conversation_id` 场景。

验收条件：

- 所有核心场景可确定性复现。
- 测试不依赖真实 Dify 服务。
- 可以调整网络分块和事件延迟以模拟代理行为。

## 6. 阶段 4：异步 Dify Chatflow 客户端

实现内容：

- 目标 Chatflow 配置解析。
- 异步 `/v1/chat-messages` 调用。
- API Key 注入。
- 子 SSE 事件迭代器。
- 连接、读取和总时长超时。
- 取消与连接清理。
- 子停止接口调用。
- 结构化错误分类。

验收条件：

- 可以消费模拟 Chatflow 的完整响应。
- 能区分 HTTP 失败、SSE `error`、流中断和正常完成。
- 取消后上游连接被释放。
- 密钥不会出现在普通日志中。

## 7. 阶段 5：路由抽象

实现内容：

- 路由服务接口。
- 有序多标签路由结果模型。
- 路由 ID 白名单校验。
- 阈值和最大路由数量限制。
- 静态路由实现，用于无真实路由 Chatflow 时测试。
- Dify 路由 Chatflow 适配器占位或实现，取决于可用测试环境。

验收条件：

- 输入同一静态路由结果时，编排顺序稳定。
- 未注册路由无法触发任意外部调用。
- 空路由和路由失败有明确兜底行为。

## 8. 阶段 6：串行聚合编排器

实现内容：

- 创建公共 task/message/conversation/workflow run ID。
- 发送公共 `workflow_started`。
- 按路由顺序输出 Markdown 标题。
- 串行消费子 Chatflow。
- 将子 `message.answer` 转换成公共 `message`。
- 截留子流程和节点事件。
- 截留子 `message_end`。
- 等待子 `workflow_finished`。
- 汇总引用和 usage。
- 发送唯一公共 `message_end` 和 `workflow_finished`。
- 公共 SSE 独立心跳。

验收条件：

- 两个以上子 Chatflow 的回答按路由顺序出现。
- 首个子 Chatflow 的文本无需等待后续子 Chatflow 即可输出。
- 客户端只收到一个 `message_end`。
- 客户端只收到一套公共 ID。
- 所有成功子 Chatflow 的引用在最终 `message_end` 中出现。
- 子流程事件不会泄漏多个 `workflow_run_id`。

## 9. 阶段 7：部分成功

实现内容：

- 首字前失败提示。
- 首字后失败提示。
- 失败后继续后续路由。
- 只收集具有完整 `message_end` 的子调用引用。
- 内部部分成功状态和错误详情记录。
- 所有子调用失败时的统一回答策略。

验收条件：

- 任一子 Chatflow 失败不会使后续子 Chatflow 被跳过。
- 公共流仍正常产生 `message_end` 和 `workflow_finished`。
- 失败子调用不会污染引用列表。
- 日志可以定位具体失败路由和子任务。

## 10. 阶段 8：会话和任务映射

实现内容：

- 公共会话到各子 Chatflow 会话的映射。
- 同一公共会话的多轮调用。
- 公共任务到当前子任务的映射。
- 停止当前子调用并阻止后续路由。
- 任务完成后的映射清理。
- 过期会话和孤儿任务清理策略。

验收条件：

- 同一公共会话再次命中某个子 Chatflow 时使用原子会话 ID。
- 首次命中新 Chatflow 时创建并保存新的子会话 ID。
- 公共停止请求能够停止当前上游任务。
- 停止后不会启动剩余子 Chatflow。

## 11. 阶段 9：工程化与生产准备

实现内容：

- 反向代理流式配置示例。
- 超时和连接池调优。
- 并发限制与限流。
- 结构化日志、指标和追踪。
- 优雅关闭。
- 配置及密钥安全检查。
- 容器化和部署清单。
- 压力测试和长连接测试。

验收条件：

- 代理不会缓冲 SSE。
- 长时间串行调用期间连接保持活跃。
- 客户端断开后无持续占用的上游任务。
- 达到约定并发下没有明显连接泄漏和内存持续增长。
- 日志中不包含 API Key。

## 13. 后续优化：ID、会话状态与审计持久化

### 13.1 当前实现基线

当前版本的四类公共 ID 都在每次请求开始时通过 UUID 生成，但保存周期不同：

| ID | 当前保存位置 | 生命周期 | 容器重启影响 |
|---|---|---|---|
| `conversation_id` | `MemoryState.conversations` 的字典 key | 进程存活期间持续保留 | 公共会话到各子 Chatflow 会话的映射全部丢失 |
| `message_id` | 当前请求的局部 `ids` 字典 | 当前 SSE 请求 | 请求结束后无可查询记录 |
| `task_id` | `MemoryState.tasks` 的字典 key | 仅任务运行期间，结束后主动删除 | 活动任务无法再停止，也无法判断中断状态 |
| `workflow_run_id` | 当前请求的局部 `ids` 字典 | 当前 SSE 请求 | 请求结束后无可查询记录 |

子 Chatflow ID 的现状：

- 子 `conversation_id` 会保存到 `MemoryState.conversations`，用于多轮对话。
- 子 `task_id` 仅在当前调用期间挂到活动任务，用于转发停止请求，完成后清空。
- 子 `message_id` 和子 `workflow_run_id` 当前没有落库，也没有形成完整的公共/子 ID 关联记录。
- Python 标准日志仅输出到 stdout；若容器日志没有外部采集或持久化，重建容器后无法作为可靠审计记录。

因此当前内存实现只适合单进程开发验证，不支持多 worker、多副本、滚动升级、崩溃恢复或历史查询。

### 13.2 Dify 的实现参考

Dify 将执行历史主要保存在关系数据库中，默认自托管配置使用 PostgreSQL，也支持
其他数据库配置；SQLAlchemy 是其持久化模型层。主要记录包括：

- `conversations`：应用、模型、名称/摘要、输入、来源、最终用户或账号、对话轮数、状态和时间。
- `messages`：`conversation_id`、问题、回答、模型、Token、费用、延迟、状态、错误、元数据和关联的 `workflow_run_id`。
- `workflow_runs`：工作流版本和图快照、输入/输出、状态、错误、耗时、Token、步骤数、发起人和起止时间。
- `workflow_node_executions`：逐节点的输入、过程数据、输出、状态、错误、耗时以及 Token/费用等执行元数据。
- `workflow_app_logs`：一张较薄的索引表，用于把运行关联到 workspace、app、workflow、调用来源和发起人。
- `dataset_retriever_resources`：按 `message_id` 保存知识检索引用。
- 过大的节点输入/输出可通过 `workflow_node_execution_offloads` 转移到文件/对象存储。

Dify 的 `task_id` 与上述持久化运行记录职责不同：它主要用于正在运行任务的停止与归属校验。
当前源码通过 Redis 保存任务归属和停止标记，并通过 GraphEngine 的 Redis 命令通道停止工作流；
真正用于历史查询和审计关联的是 `message_id`、`conversation_id` 和 `workflow_run_id`。

Dify 还通过 Celery 的 `workflow_storage` 队列异步保存或更新工作流运行，失败时重试，
以减少主响应链路的数据库写入压力。需要注意，Dify 的 Logs 更接近“应用运行历史和排障记录”，
不是天然不可篡改的合规审计账本。

参考：

- [Dify 日志说明](https://github.com/langgenius/dify-docs/blob/main/en/cloud/use-dify/monitor/logs.mdx)
- [Conversation 与 Message 数据模型](https://github.com/langgenius/dify/blob/main/api/models/model.py)
- [WorkflowRun、节点执行与 WorkflowAppLog 数据模型](https://github.com/langgenius/dify/blob/main/api/models/workflow.py)
- [工作流运行异步持久化任务](https://github.com/langgenius/dify/blob/main/api/tasks/workflow_execution_tasks.py)
- [运行任务停止与 Redis 控制](https://github.com/langgenius/dify/blob/main/api/services/app_task_service.py)

### 13.3 网关目标存储架构

生产版本建议采用“PostgreSQL 保存事实，Redis 保存短期运行状态，stdout/OTel 保存运维遥测”的分层方案：

1. PostgreSQL 作为唯一持久事实源，至少包含：
   - `gateway_conversations`：公共会话、用户、状态和时间。
   - `gateway_conversation_routes`：公共会话与各工作流子 `conversation_id` 的映射。
   - `gateway_messages`：公共 `message_id`、问题/最终回答、路由结果、用量和完成状态。
   - `gateway_runs`：公共 `workflow_run_id`、公共 `task_id`、状态、耗时和错误摘要。
   - `gateway_child_runs`：工作流名称，以及全部公共/子 conversation、message、task、run ID，HTTP 状态、首字/总耗时、用量、引用数量和错误。
   - `gateway_audit_events`：只追加的关键事件，例如请求接收、路由完成、子调用开始/结束、停止、失败和恢复。
2. Redis 仅保存活动任务、取消标记、当前子任务、分布式锁和带 TTL 的任务租约，不作为历史审计来源。
3. 应用日志改为 JSON 结构化输出，由 Docker 日志驱动或 Loki/ELK 等外部系统采集；使用公共 ID 作为关联键。
4. 可选接入 OpenTelemetry，把网关请求、意图识别和每个子 Chatflow 调用组织为同一条 trace。
5. 不逐条持久化所有 SSE 文本 chunk；默认保存最终拼接结果和生命周期事件，只有排障模式才短期保存原始事件。

SQLite 只适合单实例本地验证。考虑后续 Docker Compose、多 worker 和并行调用，正式方案直接采用 PostgreSQL；
数据库迁移使用 Alembic，避免依赖启动时自动建表。

### 13.4 安全与保留策略

- 永不保存 API Key、Authorization 头或完整配置快照。
- 问题、回答、节点输入/输出可能包含敏感信息，需要支持“全文、脱敏、仅哈希、不保存”四档策略。
- IP、User-Agent 等访问上下文按实际审计需求决定是否保存；IP 建议支持掩码或哈希。
- 错误详情区分对外安全文案与内部诊断信息，内部堆栈不得回传调用方。
- 为会话、消息、运行和审计事件分别配置保留天数，定时分批清理并记录清理审计。
- 数据库需要备份、恢复演练、访问权限隔离；若有合规要求，再增加归档、签名或 WORM 存储。

### 13.5 实施顺序

1. **P0：关系模型与 ID 全链路**——先落库公共会话/消息/运行和子运行映射；补齐当前遗漏的子 `message_id`、子 `workflow_run_id`。
2. **P0：可靠生命周期写入**——请求开始先创建 `running` 记录，结束更新为 `succeeded`、`partial_succeeded`、`failed` 或 `stopped`；启动时将超时的 `running` 标记为 `interrupted`。
3. **P1：Redis 活动任务协调**——支持多 worker 下的停止请求、任务租约和并发控制；容器重启后明确返回“任务已中断”，而不是误报不存在。
4. **P1：结构化审计事件**——形成可按公共 ID、用户、工作流、状态和时间检索的事件链，并对敏感字段执行统一脱敏。
5. **P1：查询与运维接口**——先提供内部管理查询，不立即复制 Dify 全部会话管理 API。
6. **P2：异步写入与可观测性**——在吞吐量需要时引入持久队列/任务 worker，并接入 OTel、指标和日志平台。
7. **P2：保留与归档**——实现分批清理、长期归档、备份恢复和容量告警。

验收条件：

- 重启容器后，多轮请求仍能找到每个子 Chatflow 的 `conversation_id`。
- 任一公共 ID 都能查询到对应的全部子 ID、路由顺序、状态和时间。
- 多 worker 环境中停止请求能够定位并停止当前子任务。
- 进程异常后不存在永久停留在 `running` 的记录。
- 审计查询不依赖容器本地日志文件，且日志和数据库中均无密钥。
- 保留策略可配置、可测试、可观察，并能从备份恢复关键关联数据。

## 14. 后续路线：并行调用、顺序回放

第一阶段稳定后再实施。

实现方向：

- 同时启动所有命中的子 Chatflow。
- 每个子调用使用独立有界队列保存事件。
- 严格按照路由顺序消费和输出队列。
- 当前路由未完成时，后续路由继续在后台生产事件。
- 轮到后续路由时，先回放已有 chunk，再切换为实时消费。
- 引用仍在所有路由完成后统一返回。

新增风险：

- 后续路由输出过大导致内存压力。
- 客户端消费过慢造成背压。
- 多任务取消和连接清理更复杂。
- 需要磁盘溢写或其他持久缓冲机制。
- 服务重启时缓冲内容和上游任务可能丢失。

并行化验收条件应至少包括：

- 输出顺序与串行版本完全一致。
- 首个路由的首字时间不劣于串行版本。
- 后续路由已提前完成时可立即回放。
- 缓冲达到上限时行为明确且不会耗尽内存。
- 停止请求能够取消全部并行子任务。

## 15. 后续优化：流式输出节奏控制

### 15.1 背景与目标

真实联调中，使用 `curl -N` 直连本机 Uvicorn 的 `/v1/chat-messages`，一次请求在约 174 秒内收到 4,526 条 `message`，其中 3,251 次相邻到达间隔小于 5 毫秒；客户端会看到短文本成批出现。模拟上游按约 150 毫秒间隔发送 SSE 时，网关能够逐条转发，因此节奏控制应作为可选的输出体验层，同时保留对上游批量到达原因的排查能力。

目标是在不改变回答内容、工作流顺序和 Dify SSE 协议的前提下，将突发到达的 `message.answer` 平滑输出。Dify 的单条 `message` 不等于单个模型 token。本实现以模型无关的文本单位近似计数：连续字母数字视作一个单位，CJK 字符和标点各视作一个单位，空白连续段视作一个单位；因此配置项虽沿用 token 命名，速率是阅读节奏近似值，不等于模型 tokenizer 的精确 token/s。需要精确 token 限速时，应为实际模型配置对应 tokenizer。

### 15.2 拟定实现

- 持续异步读取上游 SSE，只将 `message.answer` 放入当前请求的文本缓冲，由独立发送调度器按单调时钟输出；不在上游读取循环中逐 token `sleep`。
- 按可安全显示的边界切分文本，避免拆坏 Unicode 字符、换行和 Markdown 内容；输出片段按原顺序拼接后必须与上游回答完全一致，不丢失、不重复。
- 每个公共请求单独维护速率和有界缓冲；缓冲达到上限时施加背压或按明确的追赶策略排空，不得无限占用内存或静默丢弃文本。
- 提供 `strict` 和 `adaptive` 两种模式：严格模式保持配置速率；体验模式以 7 单位/秒起步，在积压超过阈值时逐步加速。速率、积压阈值、缓冲上限和功能开关均应可配置。已落地的默认配置为 `adaptive`、7 单位/秒、28 单位/秒上限、35 单位积压阈值和 512 个缓冲单位。
- 公共 `workflow_started`、章节标题和心跳无需等待文本限速；当前子流程文本排空后再输出后续流程的标题与文本。`message_end`、`workflow_finished` 必须在所有待发文本之后发送，引用及 usage 结构保持原有语义。
- 停止请求和客户端断开应立即取消上游调用与发送调度，清理待发缓冲；发生上游错误时，先保证已接收文本的顺序，再按现有部分成功策略发送提示。
- 记录上游事件到达、网关发送、缓冲长度和实际输出速率等指标，用于区分上游批量到达、网关排队与客户端侧缓冲；日志不记录密钥或默认记录完整回答。

严格限速会明显延长长回答的完成时间。按本次 4,526 条 `message` 各算一个输出单位粗估，6–8 单位/秒需要约 9–13 分钟；实际单位数与模型 token 数、`message` 条数都未必相同。不能同时保证严格 6–8 单位/秒和短时间排空长回答，默认采用体验模式。

验收条件：

- 模拟上游一次突发大量 `message` 时，客户端收到的文本按配置节奏输出，且拼接结果与原文完全一致。
- 模拟上游本来就缓慢输出时，网关不额外积攒成批，也不增加不必要的首字延迟。
- 多工作流标题、文本、唯一公共 `message_end` 和 `workflow_finished` 的顺序正确；心跳不受文本限速阻塞。
- 长回答、慢客户端、缓冲上限、停止请求、客户端断开和上游中断均可确定性测试，且不会造成内存持续增长或上游连接泄漏。
- 实测记录严格模式与体验模式的首字时间、总时长、最大积压和实际输出速率，再决定默认配置。

## 16. 第一阶段完成定义

同时满足以下条件时，串行 MVP 才算完成：

- FastAPI 暴露可调用的 `/v1/chat-messages`。
- 支持有序、多标签路由结果。
- 至少两个模拟子 Chatflow 可以串行流式聚合。
- 输出包含 Markdown 章节标题。
- 只产生一个公共 `message_end`。
- 成功子调用的引用被完整汇总和重新编号。
- 单个子调用失败时继续执行并返回错误提示文字。
- 公共 ID 在整条流中一致。
- 支持多轮公共会话映射。
- 支持停止当前任务且不再启动剩余路由。
- 客户端断开后资源被清理。
- 核心协议和异常路径具有自动化测试。
- 文档与实际实现一致。
