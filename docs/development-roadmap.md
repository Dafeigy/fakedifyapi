# FakeDifyAPI 开发路线

## 1. 路线原则

- 第一阶段只实现已经确认的 Chatflow 串行聚合能力。
- 先稳定协议解析与事件状态机，再连接真实 Dify。
- 缺少真实 Chatflow 时使用模拟服务和协议夹具开发。
- 业务逻辑与 FastAPI/SSE 传输层分离，为未来并行化保留空间。
- 每个阶段必须有独立、可自动验证的验收条件。
- 开发规范确认前，不锁定代码目录、依赖管理、格式化和 CI 方案。

## 2. 阶段 0：开发规范确认

在正式编码前确定：

- Python 版本。
- 包和虚拟环境管理方式。
- 源码与测试目录结构。
- 命名、类型标注和异常处理约定。
- 格式化、lint、静态类型检查和测试工具。
- 配置及密钥加载方式。
- Git 分支、提交和评审规范。
- Docker 与部署目标。

交付物：

- 项目开发规范文档。
- 基础工具和目录约定。

验收条件：

- 后续阶段不会因基础规范缺失而产生互相冲突的实现方式。

## 3. 阶段 1：FastAPI 项目骨架

实现内容：

- FastAPI 应用入口。
- 健康检查端点。
- 配置模型和启动校验。
- 统一日志上下文。
- 网关 API Key 鉴权骨架。
- `/v1/chat-messages` 路由占位。
- `/v1/chat-messages/{task_id}/stop` 路由占位。

验收条件：

- 应用能够本地启动。
- 配置缺失时给出明确启动错误。
- 未授权调用被拒绝。
- 测试可以在不访问外部网络的情况下运行。

## 4. 阶段 2：Dify Chatflow 协议模型与 SSE 编解码

实现内容：

- Chatflow 请求模型。
- 公共 SSE 事件模型。
- Dify 子事件的宽松解析模型。
- SSE 增量解析器。
- SSE 序列化器。
- `event: ping` 支持。
- 跨 TCP chunk、跨行和大 `message_end` 的解析测试。
- 未知事件兼容策略。

验收条件：

- 任意网络分块方式下，同一组 SSE 输入都解析成相同事件序列。
- `message_end` 中的大型引用数组不会被截断。
- 未知字段不会导致整个流解析失败。
- 输出帧符合 `data: <json>\n\n` 或 `event: ping\n\n` 格式。

## 5. 阶段 3：模拟 Dify Chatflow

实现内容：

- 可配置的模拟 Chatflow 服务或测试应用。
- 正常流式响应场景。
- 多引用和无引用场景。
- 首字前失败、首字后失败和流中断场景。
- 延迟、ping 和大事件场景。
- 停止任务场景。
- 多轮 `conversation_id` 场景。

验收条件：

- 所有核心场景可确定性复现。
- 测试不依赖真实 Dify 服务。
- 可以调整网络分块和事件延迟以模拟代理行为。

## 6. 阶段 4：异步 Dify Chatflow 客户端

实现内容：

- 目标 Chatflow 配置解析。
- 异步 `/v1/chat-messages` 调用。
- API Key 注入。
- 子 SSE 事件迭代器。
- 连接、读取和总时长超时。
- 取消与连接清理。
- 子停止接口调用。
- 结构化错误分类。

验收条件：

- 可以消费模拟 Chatflow 的完整响应。
- 能区分 HTTP 失败、SSE `error`、流中断和正常完成。
- 取消后上游连接被释放。
- 密钥不会出现在普通日志中。

## 7. 阶段 5：路由抽象

实现内容：

- 路由服务接口。
- 有序多标签路由结果模型。
- 路由 ID 白名单校验。
- 阈值和最大路由数量限制。
- 静态路由实现，用于无真实路由 Chatflow 时测试。
- Dify 路由 Chatflow 适配器占位或实现，取决于可用测试环境。

验收条件：

- 输入同一静态路由结果时，编排顺序稳定。
- 未注册路由无法触发任意外部调用。
- 空路由和路由失败有明确兜底行为。

## 8. 阶段 6：串行聚合编排器

实现内容：

- 创建公共 task/message/conversation/workflow run ID。
- 发送公共 `workflow_started`。
- 按路由顺序输出 Markdown 标题。
- 串行消费子 Chatflow。
- 将子 `message.answer` 转换成公共 `message`。
- 截留子流程和节点事件。
- 截留子 `message_end`。
- 等待子 `workflow_finished`。
- 汇总引用和 usage。
- 发送唯一公共 `message_end` 和 `workflow_finished`。
- 公共 SSE 独立心跳。

验收条件：

- 两个以上子 Chatflow 的回答按路由顺序出现。
- 首个子 Chatflow 的文本无需等待后续子 Chatflow 即可输出。
- 客户端只收到一个 `message_end`。
- 客户端只收到一套公共 ID。
- 所有成功子 Chatflow 的引用在最终 `message_end` 中出现。
- 子流程事件不会泄漏多个 `workflow_run_id`。

## 9. 阶段 7：部分成功

实现内容：

- 首字前失败提示。
- 首字后失败提示。
- 失败后继续后续路由。
- 只收集具有完整 `message_end` 的子调用引用。
- 内部部分成功状态和错误详情记录。
- 所有子调用失败时的统一回答策略。

验收条件：

- 任一子 Chatflow 失败不会使后续子 Chatflow 被跳过。
- 公共流仍正常产生 `message_end` 和 `workflow_finished`。
- 失败子调用不会污染引用列表。
- 日志可以定位具体失败路由和子任务。

## 10. 阶段 8：会话和任务映射

实现内容：

- 公共会话到各子 Chatflow 会话的映射。
- 同一公共会话的多轮调用。
- 公共任务到当前子任务的映射。
- 停止当前子调用并阻止后续路由。
- 任务完成后的映射清理。
- 过期会话和孤儿任务清理策略。

验收条件：

- 同一公共会话再次命中某个子 Chatflow 时使用原子会话 ID。
- 首次命中新 Chatflow 时创建并保存新的子会话 ID。
- 公共停止请求能够停止当前上游任务。
- 停止后不会启动剩余子 Chatflow。

## 11. 阶段 9：工程化与生产准备

实现内容：

- 反向代理流式配置示例。
- 超时和连接池调优。
- 并发限制与限流。
- 结构化日志、指标和追踪。
- 优雅关闭。
- 配置及密钥安全检查。
- 容器化和部署清单。
- 压力测试和长连接测试。

验收条件：

- 代理不会缓冲 SSE。
- 长时间串行调用期间连接保持活跃。
- 客户端断开后无持续占用的上游任务。
- 达到约定并发下没有明显连接泄漏和内存持续增长。
- 日志中不包含 API Key。

## 12. 阶段 10：真实 Dify 联调

待具备真实 Chatflow 后执行。

需要的最小环境：

- 明确的 Dify 版本。
- 至少两个可调用 Chatflow。
- 至少一个启用知识库及引用展示。
- 可以制造正常、无引用和失败场景。
- 可以测试多轮会话和停止生成。

联调内容：

- 固定实际事件顺序和可选字段。
- 核验 `message_end` 引用结构。
- 核验 `workflow_finished` 状态。
- 核验子 Chatflow 的停止行为。
- 核验真实代理和网络分块。
- 核验多轮 `conversation_id`。
- 录制脱敏 SSE 作为回归夹具。

验收条件：

- 与目标 Dify 客户端或现有业务调用方兼容。
- 真实引用能够在公共 `message_end` 中完整展示。
- 串行多 Chatflow 行为与模拟测试一致。
- 发现的版本差异被记录并纳入测试。

## 13. 后续路线：并行调用、顺序回放

第一阶段稳定后再实施。

实现方向：

- 同时启动所有命中的子 Chatflow。
- 每个子调用使用独立有界队列保存事件。
- 严格按照路由顺序消费和输出队列。
- 当前路由未完成时，后续路由继续在后台生产事件。
- 轮到后续路由时，先回放已有 chunk，再切换为实时消费。
- 引用仍在所有路由完成后统一返回。

新增风险：

- 后续路由输出过大导致内存压力。
- 客户端消费过慢造成背压。
- 多任务取消和连接清理更复杂。
- 需要磁盘溢写或其他持久缓冲机制。
- 服务重启时缓冲内容和上游任务可能丢失。

并行化验收条件应至少包括：

- 输出顺序与串行版本完全一致。
- 首个路由的首字时间不劣于串行版本。
- 后续路由已提前完成时可立即回放。
- 缓冲达到上限时行为明确且不会耗尽内存。
- 停止请求能够取消全部并行子任务。

## 14. 第一阶段完成定义

同时满足以下条件时，串行 MVP 才算完成：

- FastAPI 暴露可调用的 `/v1/chat-messages`。
- 支持有序、多标签路由结果。
- 至少两个模拟子 Chatflow 可以串行流式聚合。
- 输出包含 Markdown 章节标题。
- 只产生一个公共 `message_end`。
- 成功子调用的引用被完整汇总和重新编号。
- 单个子调用失败时继续执行并返回错误提示文字。
- 公共 ID 在整条流中一致。
- 支持多轮公共会话映射。
- 支持停止当前任务且不再启动剩余路由。
- 客户端断开后资源被清理。
- 核心协议和异常路径具有自动化测试。
- 文档与实际实现一致。
